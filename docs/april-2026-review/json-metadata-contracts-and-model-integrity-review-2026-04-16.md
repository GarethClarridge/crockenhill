# JSON Metadata Contracts And Model / Data-Integrity Boundary Review

Date: 2026-04-16

Read-only review. The March 2026 review artifacts were used as baseline context only, and resolved issues were not repeated unless they still exist in the current code. Laravel Boost MCP resources were not exposed in this session, so schema and model/database context came from current migrations, models, query code, and integrity tests, with current official Laravel documentation checked before making Laravel-convention judgments.

The current JSON-backed columns inspected in this pass were `songs.import_metadata`, `service_sections.source_segment_ids`, `service_sections.metadata`, `church_services.import_metadata`, `church_service_items.metadata`, `livestream_segments.metadata`, `inbound_emails.processing_metadata`, and the `media_processing_logs` JSON fields (`ai_analysis`, `processing_metadata`, `rms_stats`, `visual_samples`, and `song_clusters`).

The risky JSON contract surface is now much narrower than it was in March. The remaining live cross-module contracts are concentrated in `church_services.import_metadata`, `church_service_items.metadata`, `service_sections.metadata`, and `media_processing_logs.processing_metadata`. Other JSON columns inspected in this pass looked more local, typed, or append-only.

## Findings

### [P1] `media_processing_logs` still has dual identity authorities for extracted date/service, and new runtime writes still favor JSON over the promoted columns

`MediaProcessingLog` now exposes first-class `extracted_date` and `extracted_service` attributes, but the main creation path still writes extracted identity into `processing_metadata` rather than those columns. The read side still treats JSON as a live fallback: `MediaProcessingIdentityResolver` resolves from columns or JSON, and `SermonCreationService` still reads `processing_metadata['extracted_date']` and `processing_metadata['extracted_service']` before any column-based path. That means the most important identity contract for matching processing runs to services is still effectively duplicated across a typed column boundary and a JSON payload boundary. The risk is no longer “missing columns”; it is drift and migration-safety, because new code can still behave correctly with stale or null columns as long as the JSON copy happens to exist.

### [P1] `church_services.import_metadata.pending_structure_merge` is still a live workflow-state contract, not just historical metadata

The pending-merge payload is now wrapped by `ChurchServiceImportMetadata` and `PendingStructureMergeMetadata`, which improves discoverability, but it is still functioning as real operator workflow state inside JSON. `ChurchServiceStructureMergeService` stages a structured `pending_structure_merge` payload into `import_metadata`, `ResolvePendingStructureMerge` reads it to drive resolution, and both the review dashboard and the admin list query for pending merges with JSON-path checks. In practice, this blob now behaves like a domain state machine boundary: it controls review visibility, resolution choices, and UI badges. Because that state is still hidden inside `import_metadata`, it remains harder to index, validate, and evolve safely than the review-state and canonical-conflict columns that were promoted out of JSON in March.

### [P1] `livestream_projection` metadata is still acting like a relational provenance contract across services, items, and deletion flows

The livestream projection path now looks more intentional than it did in March, but it still depends on hidden JSON keys to model ownership and provenance. `LivestreamSectionToServiceItemMapper` writes `processing_id`, `service_section_id`, `source_segment_ids`, `confidence_level`, and `needs_manual_review` into `church_service_items.metadata.livestream_projection`, while `LivestreamChurchServiceProjectionService` writes a service-level `livestream_projection` object into `church_services.import_metadata`. Those same keys are then used to relink sections to items, recover fallback processing IDs on the show page, and locate projected items for destructive cleanup via a JSON-path query. This is relation-like behavior without relation-like structure: `processing_id` and `service_section_id` are effectively acting as foreign-key-grade connectors, but they are only discoverable if a reader knows the JSON shape in advance.

### [P2] `service_sections.metadata.confidence_level` is still a runtime decision contract even though `service_sections.confidence` now exists as a real column

This boundary is improved but not fully normalized. `ServiceSection` now has a numeric `confidence` column, yet the classifier still emits `metadata.confidence_level`, the extraction planner still queries for `metadata->confidence_level = 'high'`, and publication gating still checks that same metadata string. The support helper explicitly treats column confidence, `metadata.confidence_score`, and `metadata.confidence_level` as interchangeable authorities. That makes section confidence harder to trust across modules, because selection, publication, and display can still key off a legacy or derived representation instead of a single canonical measure.

### [P2] `processing_metadata` has a typed wrapper now, but it still functions as a multi-owner operational scratchpad with weak contract boundaries

`ProcessingMetadata` is a real improvement, but most of the blob is still effectively “raw” JSON. The wrapper gives first-class shape only to a small subset of keys, while multiple jobs and services continue to append, unset, and read unrelated operational values directly from the underlying array. In the current code, the same blob carries temp-file cleanup paths, reconciliation trigger history, sermon-completion timestamps, final-video paths, visual-analysis progress, and manual-review state. That means the contract is still distributed across several producers and consumers rather than owned by one workflow boundary. Discoverability is better than in March, but validation, lifecycle rules, and migration-safety are still weak because there is no clearly bounded schema for most live keys.

### [P3] Model helpers still hide compatibility fallbacks from promoted columns back into JSON, which makes source-of-truth boundaries harder to trust

The biggest March model leaks have been reduced, but several models still contain live compatibility logic that silently reads legacy JSON when first-class columns are absent. `ChurchServiceItem::semanticSectionType()` still falls back to `metadata.section_type`, `ServiceSection` still falls back from promoted alignment columns to `metadata.oosAlignment`, and `MediaProcessingLog` still mixes structured manual-review metadata with legacy error-message parsing and JSON-path query logic. None of this is wrong on its own, and some of it is clearly deliberate for older rows, but keeping these compatibility rules on the model surface means callers cannot easily tell whether they are consuming normalized persistence state or a repair/legacy interpretation.

## Open Questions

- Are `media_processing_logs.extracted_date` and `media_processing_logs.extracted_service` intended to be authoritative for all newly-created runs now, or is the JSON copy still considered an equal source of truth?
- Is `pending_structure_merge` meant to remain a long-lived operator-visible workflow state, or is it now mature enough to justify promotion into first-class service review columns/state?
- Is `livestream_projection.processing_id` durable provenance that other modules are expected to rely on, or only temporary import context that happened to become shared state?
- Should the numeric `service_sections.confidence` column become the only runtime authority, with `confidence_level` reduced to display/derived metadata only?

## What Improved Since March

The biggest improvement is that several March-era JSON contracts have genuinely been promoted into first-class schema. Reporting state that previously lived inside item and section metadata now has dedicated columns and indexes, and the promotion migration backfills from legacy JSON while auditing invalid values. That is a meaningful data-integrity improvement, not just a wrapper around the old payloads.
