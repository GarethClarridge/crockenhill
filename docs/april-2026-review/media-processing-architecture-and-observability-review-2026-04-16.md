# Media Processing Architecture And Observability Review

Date: 2026-04-16

Read-only follow-up review. The March 2026 review artifacts were used as baseline context only, and previously reported issues were not repeated unless they still exist in the current code. Laravel Boost MCP resources were not exposed in this session, so this report is based on static repository inspection plus current Laravel queue / logging convention checks.

## Findings

### [P1] Upload deduplication is still too broad and still optimistic, so the API can reuse the wrong in-flight run

All three upload entrypoints still funnel through the same `UnifiedMediaProcessor::process()` path, but the deduplication key is only `file_hash + pending/processing status`. It does not include the requested processing profile or the caller / owner scope, and the method explicitly documents a TOCTOU window between the duplicate check and log creation. In practice that leaves three remaining failure modes after the March refactor:

- the same binary uploaded to `/api/media/video` and `/api/media/livestream` can be collapsed onto one run even though those pipelines are intentionally different;
- a non-admin caller can be handed another user’s in-flight `processing_id`, while later status access is still owner-scoped;
- concurrent identical uploads can still create duplicate runs because the check is read-before-create rather than atomic.

This is now the clearest remaining idempotency risk at the upload boundary because the API surface looks unified, but the dedupe contract is still global-by-hash rather than scoped-by-intent.

Smallest safe refactor direction: make the idempotency key at least `(owner scope or token scope, pipeline profile, file_hash)` and enforce it through a durable lock or unique in-flight record instead of an optimistic preflight lookup.

### [P1] Media-processing runs still do not persist queue, job, or batch correlation, so failure diagnosis still depends on parsing log files

The March refactor centralized orchestration, but the run record is still missing durable execution correlation. `ProcessingRunOrchestrator` dispatches chains and livestream batches without persisting any returned batch ID, queue runtime metadata, or downstream job identifiers. The `media_processing_logs` schema still has no dedicated queue / batch / attempt fields, there are no queue lifecycle listeners registered at app boot, and the shared failure handler persists only terminal status plus an error message. On the operator side, `ProcessingLogService` still reconstructs run diagnostics by scanning `storage/logs/laravel.log`, and `ProcessingLogsViewer` consumes that file-derived view.

That means the architecture is safer than March in terms of state transitions, but not yet safer in terms of post-failure diagnosis. Once logs rotate, log format changes, or queue-level context is needed, the run record itself still cannot answer basic questions such as "which batch failed", "which queue handled this", or "what attempt number finally exhausted retries".

Smallest safe refactor direction: add lightweight media-run instrumentation only. Persist `queue`, `attempt`, `job_uuid`, and `batch_id` into `processing_metadata` or dedicated nullable columns via queue events or job middleware, then make the operator UI prefer that structured metadata before falling back to file parsing.

### [P2] AI-analysis failures and degraded outcomes are still poorly correlated to the actual processing run

`ProcessTranscriptWithAI` still calls `SermonAnalysisInterface` without passing any run context, and the contract itself has no place to carry one. As a result, `SermonAnalysisService` still hard-codes `processingId = 'unknown'` for the analysis step, retry-attempt logging, and API-call logging, while the mock implementation logs analysis completion without any `processing_id` at all. At the same time, the operator log viewer still filters logs by the real processing ID. So the AI stage remains the hardest part of the pipeline to diagnose from the per-run view even though it is one of the most failure-prone external boundaries.

There is also still a degraded-state visibility gap after fallback. The job writes `current_step = ai_analysis_fallback`, but the cleanup job only preserves notification-failure markers when it marks a run completed. A run that had to fall back during AI analysis therefore finishes looking like an ordinary completion unless an operator reconstructs that history from logs, and those logs are currently uncorrelated to the real run.

Smallest safe refactor direction: thread a processing context into `SermonAnalysisInterface`, use it in both real and mock implementations, and preserve a structured "completed with AI fallback" marker in run metadata or terminal step handling so degraded completions remain visible after cleanup.

### [P2] AI retry ownership is still split between the queue layer and the analysis service

`ProcessTranscriptWithAI` declares queue-level retries and backoff, but `SermonAnalysisService` still runs its own internal retry loop with exponential `sleep()` between attempts. That means one queue attempt can contain several OpenAI attempts plus in-worker wait time. The architecture is functionally resilient, but the ownership boundary is still blurry: operator-visible queue attempts do not line up cleanly with AI attempts, worker capacity is tied up during service-level sleep windows, and it is harder to reason about which retry policy actually governs the stage.

This is now more obvious because transcription has already moved closer to a single-owner retry model: `TranscribeAudio` owns queue attempts and backoff, while the underlying transcription service does one unit of work per invocation.

Smallest safe refactor direction: make `SermonAnalysisService` a single-attempt unit and move retry cadence, backoff, and any overlap protection into `ProcessTranscriptWithAI`, matching the transcription stage instead of layering two retry systems together.

## Open Questions

- Is duplicate-upload reuse meant to be global across all callers and media types, or should the intended contract be "same caller, same pipeline, same file"?
- Should `media_processing_logs` become the durable operator source of truth for queue / batch / attempt correlation, or is there a separate plan to standardize on a queue dashboard such as Horizon and keep only summary metadata in-app?
- Should AI fallback remain a silent degraded success from an operator perspective, or should a completed run that used fallback be surfaced as an explicit follow-up state?

## What Improved Since March

The architecture is materially better than the March baseline. Start, retry, reclassify, and manual-review resume now flow through a canonical orchestrator instead of several partly overlapping entrypoints, and the manual-review / reclassification paths now share the same failure handling as the primary pipelines. That is a real simplification of pipeline ownership and it reduces the chance of one restart path drifting away from the others.
