# Test Suite Architecture Review

Date: 2026-04-16

Laravel Boost MCP resources and `search-docs` were not exposed in this session, so Laravel testing-convention judgments below are based on the current repository structure, the current suite itself, and the existing project conventions.

## Findings

### P1. The suite is materially better organized than it was in March, but its top-level taxonomy still does not give a reliable boundary or cost map

The current suite is broad and valuable, but the main `phpunit.xml` split is still essentially `Feature` vs `Unit`, which no longer matches the real cost and architectural shape of the tests. The default suite runs both buckets together from [phpunit.xml](/Users/garethclarridge/Projects/crockenhill/phpunit.xml:12), while a meaningful slice of the most expensive and framework-heavy tests live under `Unit`, and at least one performance-oriented suite still lives under `Feature` in [tests/Feature/Performance/SermonPresenterPerformanceTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Performance/SermonPresenterPerformanceTest.php:14). The result is that directory names no longer tell you whether a test is a pure collaborator check, a database-backed service integration, a UI journey, or an opt-in benchmark. That weakens maintainability because the test tree is no longer communicating runtime cost or architectural boundary with enough precision.

The same issue shows up inside the largest files. [tests/Unit/Services/ChurchServiceReviewStateServiceTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Unit/Services/ChurchServiceReviewStateServiceTest.php:11) is a true small-scope unit test against a plain service, but [tests/Unit/Services/ChurchServiceCanonicalUpdateServiceTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Unit/Services/ChurchServiceCanonicalUpdateServiceTest.php:22), [tests/Unit/Services/ChurchServiceReconciliationDispatcherTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Unit/Services/ChurchServiceReconciliationDispatcherTest.php:18), and especially the very large `Unit` service suites now behave more like service-level integration tests. The suite still gives useful feedback, but the taxonomy does not yet help a maintainer predict cost, scope, or failure ownership.

### P1. The fixture strategy is now noticeably stronger, but the scenario-builder layer is not yet the default authoring path in the most expensive suites

The test-support layer is a real improvement. [tests/Traits/BuildsTestScenarios.php](/Users/garethclarridge/Projects/crockenhill/tests/Traits/BuildsTestScenarios.php:19) gives the suite a reusable vocabulary for verified admins, media uploads, church-service graphs, processing logs, and service sections. That is exactly the kind of design asset a long-lived Laravel suite needs. It is already paying off in high-value flows such as [tests/Feature/Livewire/AdminChurchServiceTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Livewire/AdminChurchServiceTest.php:53) and [tests/Feature/Api/MediaUploadTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Api/MediaUploadTest.php:16), where the setup reads more like domain intent than raw record plumbing.

The remaining maintainability drag is that this pattern has not yet become the dominant path in adjacent large suites. [tests/Feature/Livewire/AdminServiceReviewDashboardTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Livewire/AdminServiceReviewDashboardTest.php:26) still builds complex service, run, and section graphs inline, and the same style persists in several heavy service tests. That means the suite now has two competing fixture dialects: scenario builders in some places, bespoke record construction in others. The architectural direction is good, but until the largest suites converge on the support layer, runtime cost and maintenance cost will stay higher than they need to be because setup logic is still duplicated near the point of use.

### P2. The church-service and review surface now matches the real application boundaries much better, but old broad suites still overlap the newer focused seams

This is the clearest improvement since March. The production code now expresses the review surface through explicit collaborators in [app/Livewire/Admin/ChurchServices/ServiceReviewDashboard.php](/Users/garethclarridge/Projects/crockenhill/app/Livewire/Admin/ChurchServices/ServiceReviewDashboard.php:57), and the tests increasingly mirror that structure with focused suites such as [tests/Feature/Actions/ServiceReview/SaveServiceSectionTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Actions/ServiceReview/SaveServiceSectionTest.php:23), [tests/Feature/Queries/ServiceReviewDashboardQueryTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Queries/ServiceReviewDashboardQueryTest.php:22), and the narrower Livewire-facing suites under `tests/Feature/Livewire/Admin/ChurchServices`.

That is a healthy architectural move because the tests now align with the way the app actually decomposes responsibilities. The remaining issue is not absence of coverage; it is overlap. The older broad suites in [tests/Feature/Livewire/AdminServiceReviewDashboardTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Livewire/AdminServiceReviewDashboardTest.php:26) and [tests/Feature/Livewire/AdminChurchServiceTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Livewire/AdminChurchServiceTest.php:53) still carry a large amount of end-to-end responsibility even after the newer collaborator-focused suites landed. As a design asset, this means the suite now tells two stories at once: the newer extracted architecture, and the older monolithic component boundary. Confidence is better than March, but maintainability will stay uneven until those stories are deliberately balanced.

### P2. Security, read-path, media-status, and JSON-shape coverage are now first-class strengths, but there is still one notable contract asymmetry

The suite is now much closer to the app's real architectural risk surface. The public read side is protected by explicit invariant tests in [tests/Feature/PublicReadSideInvariantsTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/PublicReadSideInvariantsTest.php:20), with cache-behavior checks in [tests/Feature/PublicPageReadModelCacheTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/PublicPageReadModelCacheTest.php:12) and [tests/Feature/PublicMeetingReadModelCacheTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/PublicMeetingReadModelCacheTest.php:13). Read-path performance correctness is also being guarded directly by [tests/Feature/SermonListingNPlusOneTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/SermonListingNPlusOneTest.php:13) and [tests/Feature/SermonEagerLoadingTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/SermonEagerLoadingTest.php:14). On the security side, [tests/Feature/Security/SecurityHeadersTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Security/SecurityHeadersTest.php:10), [tests/Feature/Api/RateLimitingTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Api/RateLimitingTest.php:18), and [tests/Feature/Api/MailgunInboundWebhookControllerTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Api/MailgunInboundWebhookControllerTest.php:16) now cover behaviors that genuinely matter to the deployed system rather than only internal mechanics. Media-processing contract coverage is likewise stronger and more architecture-aware in [tests/Feature/MediaProcessing/MediaProcessingStatusTransitionsTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/MediaProcessing/MediaProcessingStatusTransitionsTest.php:18), while JSON-wrapper/resource behavior is now intentionally protected in [tests/Unit/Models/StableJsonMetadataWrappersTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Unit/Models/StableJsonMetadataWrappersTest.php:16) and [tests/Unit/Http/Resources/SermonResourceTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Unit/Http/Resources/SermonResourceTest.php:15).

The main remaining asymmetry is that church-service API contracts still rely mostly on controller-level structure assertions in [tests/Feature/Api/ChurchServiceControllerTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Feature/Api/ChurchServiceControllerTest.php:89), while the underlying resources in [app/Http/Resources/ChurchServiceResource.php](/Users/garethclarridge/Projects/crockenhill/app/Http/Resources/ChurchServiceResource.php:13) and [app/Http/Resources/ChurchServiceItemResource.php](/Users/garethclarridge/Projects/crockenhill/app/Http/Resources/ChurchServiceItemResource.php:13) do not yet have the same direct contract-focused unit coverage that sermons now have. Request authorization coverage has a similar feel: it exists, but the tests in [tests/Unit/Http/Requests/RequestAuthorizationTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Unit/Http/Requests/RequestAuthorizationTest.php:11) and [tests/Unit/UpdateSermonRequestTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Unit/UpdateSermonRequestTest.php:11) still lean on partial mocks more than public HTTP seams or richer request-level integration boundaries. This is not a major gap anymore, but it is the clearest place where the suite is less boundary-faithful than the rest of the current test architecture.

### P2. The suite now gives meaningful confidence alongside phpstan and pint, but the performance layer is still the weakest part of the architecture story

Compared with March, the test suite is no longer leaning on static analysis and formatting as a substitute for architectural confidence. The combination of read-path invariants, security coverage, media workflow status checks, metadata wrapper tests, and container/glue tests such as [tests/Unit/Providers/MediaProcessingServiceProviderTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Unit/Providers/MediaProcessingServiceProviderTest.php:17) means the suite now validates a much larger portion of the app's actual seams. In its current state, phpstan and pint look like strong companions to the suite rather than the primary structural backstop.

The weakest area is the performance layer. PHPUnit now has a dedicated performance suite in [phpunit.xml](/Users/garethclarridge/Projects/crockenhill/phpunit.xml:30), which is an improvement, but the implementation is still incoherent. [tests/Performance/LivestreamProcessingPerformanceTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Performance/LivestreamProcessingPerformanceTest.php:7) targets a service reference that no longer exists in `app/Services`, mixes wall-clock and memory assertions with console output, and reads more like a historical benchmark harness than a current architectural test. [tests/Performance/ThumbnailGenerationPerformanceTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Performance/ThumbnailGenerationPerformanceTest.php:26) is explicitly opt-in skipped and spends much of its effort reflecting into private methods from [tests/Performance/ThumbnailGenerationPerformanceTest.php](/Users/garethclarridge/Projects/crockenhill/tests/Performance/ThumbnailGenerationPerformanceTest.php:81). The supporting document at [tests/README_THUMBNAIL_TESTS.md](/Users/garethclarridge/Projects/crockenhill/tests/README_THUMBNAIL_TESTS.md:46) is also stale enough to reference nonexistent `tests/Integration/*` paths. So while the core suite is now a credible design asset, the performance slice should still be treated as a secondary, non-authoritative layer until it is brought back into line with current app boundaries.

## Open Questions

- Is the long-term intent for `Unit` to mean pure collaborator-level tests, or is it intentionally being used as a home for service-level Laravel integrations as well?
- Should the broad Livewire suites for church services and service review remain as high-level journey tests, or should they be deliberately slimmed now that focused action and query suites exist?
- Is the performance directory meant to be an actively trusted part of CI architecture, or a mostly manual benchmark sandbox that happens to live under PHPUnit?
