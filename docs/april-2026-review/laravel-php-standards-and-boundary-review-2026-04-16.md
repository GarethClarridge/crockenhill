# Laravel / PHP Standards And Boundary Review

Date: 2026-04-16

Read-only review. The March 2026 review artifacts were used as baseline context only, and resolved issues were not repeated unless they still exist in the current code. Laravel Boost MCP resources were not exposed in this session, and Sail runtime introspection was unavailable because Docker was not running, so this report is based on static repository inspection plus current official Laravel / Livewire documentation checks.

## Findings

### [P1] Admin sermon editing still coordinates write-side behavior inside the Livewire component

`EditSermon` is cleaner than the March baseline, but it still acts as the application service for sermon editing. The component loads presenter-derived state during `mount()`, resolves preacher identity and scripture identity during `save()`, persists the model directly, dispatches follow-up enrichment, triggers thumbnail rendering / regeneration, queues video-quality reassessment, and assembles preview URLs for thumbnail candidates itself. That means Livewire request cycles are still the place where sermon-edit workflow rules live, which makes the edit flow harder to reuse from non-Livewire entrypoints and keeps storage / workflow knowledge coupled to the UI layer.

### [P1] The media-processing API surface still splits validation and authorization between routes, controller helpers, and one-off request logic

`MediaController` now has a good service boundary underneath it, but the HTTP boundary is still uneven. `status()` uses `MediaStatusRequest`, while `upload()`, `cancel()`, `retry()`, and `confirmSegment()` all use raw `Request` objects and perform inline validation or manual UUID checks in the controller. The controller also re-checks bearer-token ability even though the routes already carry Sanctum ability middleware, and the codebase already contains a `ProcessMediaRequest` that encapsulates similar upload rules for the admin web flow. The result is that media endpoint contracts are still spread across middleware, controller methods, helper methods, and one existing Form Request rather than one request object per endpoint.

### [P2] Routed admin Livewire components still duplicate the admin middleware contract that the route layer already enforces

The routed admin surface already sits behind `auth`, `verified`, and `admin` middleware. On top of that, `WithAdminAuthorization` re-checks the same `canAccessAdmin()` rule, and representative components such as `EditSermon` call `authorizeAdmin()` in `mount()` and again in every mutating action. Because Livewire 3 persists route middleware across subsequent requests, this duplication is mostly framework tax now rather than a meaningful safety boundary. It is not currently wrong, but it adds a lot of repeated ceremony and another place for the admin contract to drift.

### [P2] Some Eloquent models still own workflow, storage, or cached UI-list helpers instead of staying as persistence primitives

The largest March model problems have been reduced substantially, but a few residual boundary leaks remain. `ServiceSection::hasExtractedMedia()` still performs storage existence checks from the model. `SermonProcessingStep` still exposes `markAs*()` methods that persist workflow transitions directly from the entity. `Preacher` still resolves storage-backed profile URLs and builds cached admin/public list shapes on the model. `Meeting` still builds the cached admin dropdown list from the model. None of these are as severe as the earlier transcript / workflow leaks, but together they show the model layer still carrying a mix of persistence, workflow, and read-model responsibilities.

### [P3] PHP standards adoption is still uneven in boundary files and a large part of the test suite

The core app code is much more consistently typed than it was earlier in the year, but the boundary layer is still patchy. Four Form Requests still omit `declare(strict_types=1)`, `AuthServiceProvider` and `EnsureUserIsAdmin` omit it too, and the test suite still has a large legacy pocket without strict types declarations (107 unit tests and 129 feature tests at the time of review). Those same request files still show older cleanup markers and mixed rule syntax. This is not a functional bug, but it is still visible PHP standards drift in exactly the files that define validation and authorization behavior.

## Open Questions

- Is the repeated `authorizeAdmin()` pattern intentional because some admin Livewire components are expected to be reusable outside routed full-page entrypoints, or can the codebase now treat them as route-bound components and rely on persistent middleware plus policies?
- Do the media-processing API endpoints need to support both first-party session-authenticated users and bearer-token clients through exactly the same controller surface? That answer determines whether the controller-side `ensureMediaProcessAbility()` checks are intentional or can be collapsed into middleware and Form Requests.
- `bootstrap/app.php` still reads `env('TRUSTED_PROXIES')` directly in [bootstrap/app.php:35](/Users/garethclarridge/Projects/crockenhill/bootstrap/app.php:35), and the test suite documents that as an intentional bootstrap exception in [tests/Unit/Config/ConfigValidationTest.php:88](/Users/garethclarridge/Projects/crockenhill/tests/Unit/Config/ConfigValidationTest.php:88). If that assumption is still correct, it should probably be called out explicitly in project conventions so it stops looking like ordinary config-rule drift.

## What Improved Since March

The codebase is meaningfully cleaner than the March baseline. The biggest improvement is that the church-service admin surface now has real `Actions` and a dedicated query object instead of pushing everything through one giant component, and those extracted boundaries are backed by focused tests. Livewire URL state has also moved to `#[Url]` across the admin listing surface, which resolves one of the clearest Livewire v2 carry-overs from the earlier review.

The other major improvement is architectural cleanup around the public read side and media-processing surface. `ProcessingLogsViewer` no longer reaches through an HTTP controller and now talks to a dedicated status service, provider responsibilities are better split (`AiServiceProvider`, `ChurchServiceDomainServiceProvider`), scheduled commands in `bootstrap/app.php` are production-gated with overlap protection, and the heaviest March-era `Sermon` model leaks have largely been removed. The remaining issues now look like boundary consistency debt, not broad architectural disorder.
