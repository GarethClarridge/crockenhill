## Context

A clean re-run of the 2026-06-14 morning service (`MediaProcessingLog 890`, `ChurchService 790`) now classifies and auto-extracts the sermon correctly (sermon §11 `conf 0.98`, children's talk §5 `conf 0.95`, 5 hymns confirmed-matched, sermon media extracted, no manual-review halt). But several rows are still weak:

- **Bible readings are detected as a type but carry no reference.** §2 recites Psalm 148 verbatim and §9 recites Joshua 2, yet both show `reading_reference = "Bible Reading"` (the generic OOS title) or nothing.
- **Prayers/notices desync the OOS alignment.** The service has four prayers that the OOS doesn't list, which cascades into `oos_structure_mismatch` and review flags on otherwise-fine sections.
- **The mission-update video ("Bibles.mp4") was split into prayer + notices** (§6/§7) because it is speech-over-video.
- **Short transition blips** (e.g. §14, a 10-second "other" between songs) add noise.

### Decisions that scope this plan (from review)

- **The order-of-service we align against is a sparse projection/slide deck** — 8 items for ~16 real sections, no prayers, generic "Bible Reading", an "Ezekiel" image, a "Bibles.mp4" media item. We **cannot enrich the source OOS** (the richer human-readable order-of-service seen earlier was *AI-generated by Gemini from the YouTube livestream*, not a real church document). Detection must get better **against the sparse OOS as-is**.
- **§5 is genuinely a children's talk.** No new "short talk" section type — the earlier Gemini labelling was simply wrong/imprecise. (Originally raised as improvement #4; **dropped**.)
- **The on-screen video may not be in the livestream feed.** It is played on the projector, not necessarily captured in the stream, so **media-interlude detection must not rely on visual analysis** — only audio characteristics, transcript cues, and OOS `media` items.
- **Transition blips stay as microsections.** Do **not** merge them into adjacent songs (unhelpful). Tag them as transitions and stop them from generating review noise.

### Out of scope

- **Richer OOS ingestion** (was improvement #3): not possible — no real richer OOS source exists.
- **A "short talk" section type** (was improvement #4): §5 is correctly a children's talk.

## Improvement 1 — Resolve scripture references for `bible_reading` sections

### Problem
`StructuralSectionAligner::align()` sets `metadata['reading_reference'] = $item->title` on a matched reading — but the OOS title is the generic *"Bible Reading"*. There is no path that derives the actual passage from the recited words, even though `app/Services/Scripture/` (`ScriptureReferenceResolver`, `ScriptureOperatorService`) exists and is used today **only for the sermon** (`FetchBibleTextForSermon` reads `$this->sermon->reference`).

### Approach
Add a dedicated job **`ResolveReadingReferences`** that runs after sections are typed and aligned, and for each `bible_reading` section:

1. Take the section transcript.
2. Ask the model for the scripture reference being read (focused, cheap prompt — "Identify the single Bible passage being read in this transcript; respond with a reference like `Joshua 2:1-24` or `null`"). Reuse the existing OpenAI call pattern (`App\Support\OpenAiChatPayload`, mirroring `SpeechSectionClassificationService`).
3. Pass the model's reference string through **`ScriptureReferenceResolver::normalize()`** (which uses `TechWilk\BibleVerseParser`) to get a canonical, parseable reference.
4. Store on the section metadata:
   - `reading_reference` — canonical reference (overrides the generic OOS title **only when** the transcript-derived reference parses).
   - `reading_reference_source` — `transcript_ai` | `oos` | `none`.
   - `reading_reference_confidence` — model confidence.
   - `reading_reference_raw` — the unparsed model output (for debugging).
5. If the OOS title was a real reference and the transcript-derived one disagrees, keep the transcript one but add a `reading_reference_conflict` review flag.

### Why AI extraction (not pure text-matching)
The resolver parses *references*, not prose. A reader often recites the passage **without announcing it** (§2 launches straight into "Praise the Lord from the heavens…"). The model can name the passage from content; the resolver then guarantees a canonical, storable form. (A future enhancement could corroborate by matching recited text against a Bible-text corpus, but that is not required for v1.)

### Chain placement
Insert in `ProcessingPipelineBuilder::buildLivestreamChainJobs()` **after `AlignWithOos`** (so we can supplement/override the generic OOS title) and **before `ExtractSermon`**:

```
… ClassifySpeechSections → ProjectLivestreamServiceStructure → AlignWithOos
   → ResolveReadingReferences   ← NEW
   → MatchSongsFromTranscript → ReclassifyIntroOutroSections → ExtractSermon …
```

Add the same step to `buildSectionReclassificationChainJobs()`.

### Config / safety
- New flag `media-processing.reading_references.enabled` (default true) and reuse the analysis-service switch so the `mock` service short-circuits in tests.
- If the AI call fails or returns unparseable text → leave `reading_reference` as the OOS fallback, set `reading_reference_source = 'none'`, never throw (non-fatal step, like other enrichment jobs).

### Edge cases
- **Benediction misread as a reading** (§16 "Praise be to the Lord God…", ~Psalm 72): model should return `null` or low confidence → no canonical reference, no false data.
- **Multiple passages** in one reading: resolver currently normalises the first passage; keep that behaviour, store the raw for later.
- **API disabled** (`services.api_bible.enabled` false only affects text fetch, not reference naming) — reference naming is independent; document the distinction.

### Files
- **Add** `app/Jobs/ResolveReadingReferences.php`.
- **Add** `app/Services/ChurchService/ReadingReferenceExtractor.php` (the AI-call + normalize wrapper; depends on `ScriptureReferenceResolver`).
- **Edit** `app/Services/Processing/ProcessingPipelineBuilder.php` (both chains).
- **Edit** `config/media-processing.php` (flag).

### Tests
- `ReadingReferenceExtractor` unit: prose reciting Psalm 148 → `Psalm 148`; Joshua 2 narrative → `Joshua 2…`; benediction → `null`; unparseable model output → `null`.
- `ResolveReadingReferences` feature: a `bible_reading` section with the §2/§9 transcripts gets `reading_reference` populated; a non-reading section is untouched; AI failure leaves OOS fallback and doesn't fail the run.

## Improvement 2 — Content-aware sequence alignment (replace the greedy two-pointer)

### Problem
`StructuralSectionAligner::align()` walks sections and items with two indices and **one-step type lookahead**. When the OOS legitimately omits items (the four prayers aren't in the slide deck), the pointers desync: each unlisted prayer is marked `unexpected_detected_section`, inflating `mismatchCount`, which drives the review-trigger and stamps `oos_structure_mismatch` across the run. The match decision is **type + position only** — it ignores transcript/title content.

### Approach
Replace the greedy walk with a **global optimal alignment** (Needleman–Wunsch) over `structuralSections × structuralItems`, then apply the **same per-pair side-effects** that exist today. Keep the current pre-filters (exclude `Song` and `Sermon` from the walk).

**Scoring matrix** (extract into `SectionItemAlignmentScorer`):
- **Match (section ↔ item):**
  - type equality → strong positive;
  - plus content similarity bonus: song title vs transcript/`song_match`, reading reference vs OOS title, notices/welcome keyword overlap;
  - `Other`-section that the OOS expects as a reclassifiable type → positive (preserves today's `oos_reclassifiable` reclassification).
- **Gap — detected section with no item** (a prayer not in the OOS): **near-zero cost** (legitimately absent from a slide deck), so it does **not** count as a structural mismatch.
- **Gap — OOS item with no detected section**: low cost (the slide existed but wasn't a distinct audio block).
- **Aligned type conflict** (both present, types incompatible): the only real **mismatch** — this is what `mismatchCount` should count.

**Backtrace → list of `(section?, item?)` pairs**, then for each pair apply the existing actions, refactored out of the current `while` loop:
- exact match → `applyMatchedItem(+0.35)`, set `reading_reference`, attach presentation-decision metadata;
- `Other` + reclassifiable expected type → reclassify, `applyMatchedItem`, metadata trace;
- type conflict → `markMismatch(…, 'oos_type_mismatch')`;
- section-only gap → no penalty (optionally tag `oos_unlisted_section` for transparency, **no** review flag);
- item-only gap → no section side-effect.

**Net effect:** songs/notices/readings anchor correctly; unlisted prayers become free insertions instead of a desync cascade; `mismatchCount` reflects only genuine conflicts, so review flags drop sharply on services like 790.

### Preserve / verify
- `SectionAlignmentBaselineRestorer` and `AlignmentTriggerCalculator` must still receive a coherent `mismatchCount` and not re-introduce flags for the now-"free" gaps.
- Sermon/children's-talk behaviour from the previous plan is unchanged (sermon excluded from walk; children's talk stays via presentation decisions).

### Files
- **Edit** `app/Services/ChurchService/StructuralSectionAligner.php` (swap walk for DP + backtrace; keep side-effect methods).
- **Add** `app/Services/ChurchService/SectionItemAlignmentScorer.php`.
- (No chain change — still invoked by `AlignWithOos`.)

### Tests
- Parity: existing `StructuralSectionAlignerTest` scenarios still pass (or are updated with justification).
- New: **sparse-OOS-with-prayers** scenario modelled on service 790 — songs/notices/reading align, prayers are free gaps with **no** `oos_structure_mismatch`, `mismatchCount` counts only true conflicts.
- New: content tie-break — two same-type items disambiguated by title/transcript similarity.

## Improvement 5 — Detect media/video interludes (audio + OOS only, no visual reliance)

### Problem
The mission video ("Bibles.mp4", OOS `pos4 type=media`) was transcribed as speech and split into `prayer` (§6) + `notices` (§7). The transcript even contains the cue "we're going to watch a video in just a moment".

### Constraint
The video is shown on the projector and **may not be in the livestream feed**, so `PerformVisualAnalysis` cannot be assumed to see it. Detection must use **audio + transcript + OOS** signals only.

### Approach
1. **OOS-anchored (primary signal):** the OOS already carries `type=media` items (`section_type=other`, e.g. "Bibles.mp4"). With the content-aware aligner (#2), align the detected block(s) sitting at that position to the media item and **tag** them rather than leaving them as prayer/notices:
   - set `metadata['media_interlude'] = true`, `metadata['media_title'] = $item->title`;
   - represent as `ServiceSectionType::Other` + the metadata flag (no new enum case — avoids enum churn and matches the "don't add types we don't need" decision).
2. **Transcript cue (corroborating signal):** detect lead-in phrases ("watch a video", "play the video", "video clip", "we're going to see") near the boundary to (a) raise confidence and (b) place the interlude start. Cheap keyword pass first; can be folded into the classifier prompt context later.
3. **Audio characteristics (corroborating, optional v2):** a video's audio often differs from the room PA (different speaker(s), music bed, level). Use existing RMS/segment metadata to corroborate, but do **not** require it — keep v1 driven by OOS + transcript so it works when the video isn't in-stream.

Tagged interludes are **not extracted and not published** — they're structural context. They should also be excluded from the alignment mismatch count (an OOS media item that matched its block is a *match*, not a gap).

### Files
- **Edit** `app/Services/ChurchService/StructuralSectionAligner.php` (recognise `media` OOS items, tag matched block).
- **Add** a small `MediaInterludeCueDetector` (transcript keyword pass) used by the aligner / classification context.
- Possibly **edit** `app/Services/ChurchService/SpeechSectionClassificationService.php` to pass media cues into context (v2).

### Tests
- A block whose transcript contains a video cue, sitting at an OOS `media` item → tagged `media_interlude`, not split into prayer/notices, not flagged for review.
- No OOS media item + no cue → unchanged (still classified normally).

## Transition microsections (reframed from improvement #6)

### Decision
Keep short transition blips **as their own microsections** — do **not** merge into adjacent songs. Tag them explicitly so they stop generating review noise and are excluded from structural counting.

### Approach
A small post-pass (mirror the placement of `ReclassifyIntroOutroSections`, or fold into it). A section is a **transition** when:
- duration ≤ `media-processing.transitions.max_duration_seconds` (config, default ~15s), **and**
- `section_type = Other` with empty/near-empty transcript, **and**
- it sits between two non-speech sections (e.g. song↔song) or at an intro/outro boundary.

For a transition section:
- set `metadata['is_transition'] = true` (+ optional `transition_kind`: `inter_song`, `intro`, `outro`);
- **suppress** `needs_manual_review` for it (expected glue, not an anomaly);
- **exclude** it from the alignment walk and from `mismatchCount` (so it never reads as `unexpected_detected_section`);
- never extract, never publish.

This keeps §14 (the 10s "Ezekiel"/inter-song blip) visible in the structure as a labelled transition instead of either polluting the OOS match or being swallowed into a song.

### Files
- **Edit** `app/Jobs/ReclassifyIntroOutroSections.php` (add transition tagging) **or add** `app/Jobs/TagTransitionSections.php` if cleaner.
- **Edit** `app/Services/ChurchService/StructuralSectionAligner.php` (skip `is_transition` sections in the walk).
- **Edit** `config/media-processing.php` (`transitions.max_duration_seconds`).

### Tests
- A ≤15s `Other` section with no transcript between two songs → `is_transition=true`, `needs_manual_review=false`, not counted as a mismatch.
- A long `Other` speech section is **not** tagged a transition.

## Suggested implementation order
1. **#2 content-aware alignment** first — it's the structural foundation; #1 and #5 both lean on stable matching, and it removes the largest source of review noise.
2. **#1 reading references** — self-contained, directly fills the readings column, highest user-visible value.
3. **#5 media interludes** + **transition tagging** — both ride on the improved aligner and clean up the remaining noise.

- §14 carries `is_transition = true` and is not flagged for review.

## Risks / open questions
- **AI cost** for reading-reference naming is small (one short call per reading, ~2 readings/service) and gated by config.
- **NW alignment** is O(sections × items) — trivial at these sizes; the risk is behavioural parity, mitigated by keeping the existing per-pair side-effects and the existing test suite.
- **Benediction vs reading** (§16): rely on low model confidence to avoid a false reference; revisit if false positives appear.
- **Media interlude when the video *is* in-stream**: visual analysis could later corroborate, but v1 deliberately does not depend on it.
