## Context

We have `storage/scratch/crockenhill_orders_of_service_archive.md` — 102 order-of-service emails (2022–2026) compiled from Gmail into markdown (4,896 lines). Each entry has a `### <date heading>`, a `**Source subject:**` line, and usually `####` sections. **Only 56 of 102 entries have `####` headings**; 46 (including revised/original March pairs and Christmas entries) do not — ground-truth labelling must not assume them. Most entries contain **both** morning and evening orders; at least one ("Christmas weekend 2023") contains three orders spanning **two dates** (Sunday + Christmas morning). The file ends with `## Known gaps and attachment-only items` (not entries).

The existing pipeline: `InboundEmail` → `app/Jobs/ProcessInboundOosEmail.php` → `app/Services/Email/OosEmailParserService.php` (regex date/service extraction + LLM item extraction via `app/Services/Email/OpenAiOosEmailItemExtractor.php`, gpt-4.1-nano) → `app/Services/Email/InboundEmailImportService.php` (create or merge `ChurchService` + items). Entry points today: Mailgun webhook (never configured in prod) and the admin paste form (`app/Livewire/Admin/ChurchServices/SubmitEmailText.php`). Confidence thresholds in `config/service-tracking.php`: review 0.75, auto-import 0.90.

### Confirmed findings driving this plan

1. **Single-service-per-email gap.** `OosEmailParserService::extractService()` returns the *first* morning/evening keyword match, and the LLM extractor prompt asks for a single ordered list. Every real weekly email contains both services, so evening orders are never imported and morning imports can absorb evening items. **Decision (Gareth): fix the pipeline properly**, not a harness-only workaround.
2. **Date overflow bugs (verified empirically).** `"1 Timothy 2:11-15"` matches the numeric-date regex as day=11/month=15 and `CarbonImmutable::create(2026,15,11)` silently **overflows to 2027-03-11**. Bounds checks alone are insufficient — `31/02` also overflows. `CarbonImmutable::createSafe()` exists and throws `InvalidDateException` for invalid components (verified).
3. **Merge would degrade openlp data.** Local DB has 395 `openlp`-sourced `church_services` (2021-10-24..2026-07-05) colliding with most archive dates. `StructureMergePolicy::requiresMergePlanning()` only protects *livestream* items, so an email import into an openlp service directly overwrites items and flips `source` to `email`. **Decision (Gareth): create-only backfill.** Per review: create-only must be enforced *inside the importer* (transactionally), and the previously proposed `--merge-existing` flag is **dropped entirely** — a `needs_review` flag would not prevent the destructive sync. Merging over openlp stays out of scope.
4. **Eval-only runs must not pollute the review inbox (verified).** `ReviewInboxQuery::collectEmails()` loads all Pending+Failed emails (cap 50) and `app/Queries/AdminAttentionCounts.php` counts them. 102 archive emails left Pending would flood both. Fix: new `InboundEmailStatus::ArchiveEval = 'archive_eval'` case + migration altering the DB enum column (`database/migrations/2026_03_08_210000_create_inbound_emails_table.php` defines `enum('status', InboundEmailStatus::values())`). Both queries filter `whereIn(status, [pending, failed])`, so the new status is excluded with **zero query changes**. Lifecycle: created as `archive_eval`; successful `--import` → `Processed`; parse/import failure → stays `archive_eval` with failure metadata (never `Failed`, which would surface in the inbox). The migration's `down()` must be reversible with rows present: first `UPDATE inbound_emails SET status='rejected' WHERE status='archive_eval'` (archive-eval rows are non-operational, and `rejected` is the existing status invisible to the inbox), then narrow the enum.
5. **Ground-truth headings are themselves untrustworthy.** Verified: "Sunday 5 June 2026" was a **Friday** — body evidence (QCM Monday 13 July; the 28 June entry's "next Sunday: Joshua 5:1-12, Andrew W") shows it was really Sunday **5 July 2026**. Another entry is headed 15 March 2026 but annotated "[email title likely intended 15 February]". Ground truth needs weekday validation and explicit corrected-date handling, and flagged entries must be excluded from import.

Environment: `OPENAI_API_KEY` present in local `.env`; extraction model defaults to gpt-4.1-nano (~102 calls ≈ pennies). Eval runs use real OpenAI, cached in `InboundEmail.processing_metadata['parsing']` keyed by input hash (see Phase 2).

## Phase 1 — Archive splitter (pure, unit-testable)

**New:** `app/Services/Email/OosArchiveMarkdownParser.php`, `app/Data/OosArchiveEntry.php`

Parse the archive into 102 DTOs; stop at `## Known gaps and attachment-only items` (capture bullets as `knownGaps`, not entries). Per entry:

- **Dates, defensively:** `headingDate` (parsed from `###` heading; specials via Easter calc / 25 Dec; null if unresolvable), `correctedDate` from two sources — bracketed annotations like "[likely intended 15 February]" where determinable, **and a curated corrections map** in the parser (keyed by heading+subject) for cases where the email itself was wrong: first entry `"Sunday 5 June 2026" → 2026-07-05` with flag `source_date_discrepancy` (body evidence: QCM Monday 13 July; the 28 June entry's "next Sunday: Joshua 5:1-12, AW"). `groundTruthDate` = correctedDate ?? headingDate, and `syntheticReceivedAt` derives from *that*, so the 5 June entry gets a July `received_at` and the parser is truthfully scored wrong for extracting 5 June. **Weekday validation:** if the heading claims "Sunday" and groundTruthDate isn't a Sunday → blocking flag `weekday_mismatch`. Bracketed-annotation entries get blocking flag `date_discrepancy`. Blocked and `source_date_discrepancy` entries are evaluated (reported) but **never imported** (for the latter, the import gate `parsed date == groundTruthDate` also fails by construction — the parser extracts what the email says).
- `subject`: verbatim from `**Source subject:**` line.
- `bodyPlain`: reconstructed email body — `####` heading text as plain line, bullets kept, `**…**` stripped, `###` heading and Source-subject line **excluded** (no ground-truth leakage).
- **Ground-truth structure, stratified:** where `####` headings exist (56 entries), classify them (morning / evening incl. carols / notices / other) → `servicesPresent` + per-service item-line counts → `labelQuality: full`. For the 46 heading-less entries, a body keyword scan is **not** trustworthy ground truth — verified example: the headingless 22 Feb 2026 entry is morning-only but its notices say "Evening Service 6pm (3 John)", so a naive scan would fabricate an evening label. Partial-cohort `servicesPresent` is therefore recorded as `unverified`; these entries still count for date metrics and are parsed/evaluated for learning, but are **evaluation-only and never imported**. Optional follow-up, not in scope: hand-curate a partial entry's service labels and item lines to promote it to `labelQuality: full`, after which it becomes eligible for the normal gates. Eval metrics are stratified: date metrics for all entries; service and item-level metrics only for the `full` cohort.
- **Multi-date detection:** sections implying a different date than the entry date (e.g. "Christmas morning" inside a pre-Christmas Sunday entry) → blocking flag `multi_date` (evaluated, not imported).
- `flags` additionally: revised/original pair (15 March 2026 ×2), morning-only.
- Deterministic `syntheticMessageId` = `<oos-archive-{sha1_12(heading . subject)}@crockenhill.local>`; plus `inputHash` = sha256 of normalised subject+body — stored in metadata so **archive corrections invalidate the cached parse automatically** (re-parse when stored hash ≠ current, or when a stored `parser_version` differs; `--fresh-parse` remains as manual override).
- `syntheticReceivedAt` = groundTruthDate −2 days at 09:00 Europe/London. **Entries with null groundTruthDate are not persisted at all** — they can't produce a truthful `received_at`, can't be imported, and date-eval is meaningless; they appear in the report as `unresolved`.

## Phase 2 — Harness command

**New:** `app/Console/Commands/ImportOosArchiveCommand.php` (via `sail artisan make:command`), signature:

```
oos:import-archive {path?}
  {--dry-run}      split + validate only, no DB writes, no LLM calls
  {--import}       write to church_services (default: parse + evaluate only)
  {--fresh-parse}  force re-parse even when input hash + parser version match
  {--limit=} {--date=*} {--from=} {--to=}
  {--report=}      default storage/scratch/oos_archive_eval_{Ymd_His}.json
```

Per persisted entry, synchronously (no queue):

1. **Create or synchronise** by `syntheticMessageId` (not bare `firstOrCreate` — that would leave stale source content in place forever): on first sight, create with **status `ArchiveEval`**; on subsequent runs, if the computed `inputHash` differs from the stored one, **update `subject`, `body_plain`, `received_at`, and `processing_metadata['archive']` on the existing row before parsing** — otherwise a "fresh" parse would re-read the old database body. If the changed entry was already imported (`Processed`), do **not** touch the created services: record flag `source_updated_after_import`, surface it prominently in the report, and leave reconciliation as an explicit human decision. Ground truth (heading, dates, flags, cohort, counts, input hash, entry index) lives under `processing_metadata['archive']`.
2. Parse with hash-aware caching: reuse `InboundEmailImportService::storedParseResult()` when input hash and parser version match and not `--fresh-parse`; else `OosEmailParserService::parse()` + `storeParseResult()` (which records hash + version). Try/catch per entry; failures recorded in metadata; loop continues → resumable, idempotent.
3. With `--import`, apply the **import gates** (below); eligible entries go through `InboundEmailImportService::import()` with `createOnly: true`. Processing follows archive order deterministically, but the headingless revised/original 15 March pair remains evaluation-only unless separately curated to `labelQuality: full`.
4. Emit console table + JSON report.

**Import gates (explicit, replacing "when the report looks sane") — evaluated per plan, not per entry:** a plan imports only if — its entry has `labelQuality: full`; its service is present in the entry's verified `servicesPresent`; its entry has no blocking flags (`weekday_mismatch`, `date_discrepancy`, `source_date_discrepancy`, `multi_date`); the plan's resolved date exactly equals `groundTruthDate` and is a valid calendar date; plan service ∈ {morning, evening, other}; plan has ≥1 item; **per-plan confidence** ≥ the auto-import threshold (0.90). The email-level confidence score continues to exist only as the legacy weighted aggregate (for stored-metadata compatibility and inbox display); it plays no part in the archive gates. Partial/unverified entries are always skipped with reason `unverified_service_ground_truth`; everything else that fails a gate is skipped with a per-plan reason in the report.

## Phase 3 — Evaluation report

**New:** `app/Services/Email/OosArchiveEvaluator.php` (separate class; called by the command).

Per entry: ground-truth vs extracted date (match + method), services present vs detected (per-plan), extracted vs ground-truth item counts (full cohort), per-plan exact correctness (right service + right date + non-empty items), ordered-item quality for the full cohort (normalised title-sequence comparison against ground-truth lines), confidence + disposition, prospective song-link hit rate via `Song::canonicalizeKey` (also quantifies that hymn-book numbers in titles are unused by `ChurchServiceSongLinker` — itself a finding).

Aggregates: date accuracy % (by cohort), extraction-method histogram, false-date cases, **service precision/recall** (full cohort only; morning and evening separately — evening recall is the headline number), **auto-import precision** (full-cohort plans only: % of gate-eligible plans that are fully correct — the metric that says whether 0.90 is trustworthy), **confidence calibration** (accuracy bucketed by confidence band), disposition counts, song-link hit rate, unresolved/blocked entry list with reasons. Output: console table + JSON in `storage/scratch/`.

## Phase 4 — Fix the known bugs first (test-first)

1. **Date safety — both construction paths**: regression tests in `tests/Integration/Services/OosEmailParserServiceTest.php` for `"1 Timothy 2:11-15"` (month 15), `31/02`, `29/02/2025` (non-leap), `29/02/2024` (leap, valid), **and ISO `2025-02-31`** — then: switch `safeDate()` to `CarbonImmutable::createSafe()` (numeric + textual paths), and harden `safeDateFromFormat()` separately, because the ISO path uses it and `createFromFormat('Y-m-d', '2025-02-31')` silently overflows to 2025-03-03 (verified). Strictest simple check: require round-trip equality (`$candidate->format('Y-m-d') === $value`).
2. **Date plausibility validator** (production parser, in `OosEmailParserService`). Rationale: the real "5 June 2026" email proves fully-specified dates are trusted the most (0.94–1.0 confidence, auto-importable) and validated the least — the parser scores *how* a date was extracted, not *whether it makes sense*. A syntactically perfect wrong date creates a phantom service silently (nothing collides) and the livestream pipeline later finds no plan for the real date. After extraction, validate the resolved date:
   - **Weekday consistency**: if the matched text (or surrounding subject/body context) claims a weekday ("sunday 5th june 2026") and the resolved date falls on a different weekday → implausible. A service date that isn't a Sunday is also suspicious on its own (this church's services are Sundays plus known specials like 25 Dec) — treat as a soft signal, not a hard fail.
   - **`received_at` window**: plan emails are forward-looking and short-horizon. Resolved date before `received_at`'s calendar day, or more than N days after → implausible, where N comes from new config `service-tracking.email_parsing.max_future_days` (default 14). Boundary tests: same-day OK, +N OK, +N+1 fails, −1 day fails. (This extends the existing year-inference use of `received_at` to fully-specified dates, which currently bypass it entirely.)
   - **On failure**: do NOT auto-correct. Cap confidence at 0.74 (the existing `min(confidence, 0.74)` pattern used for missing date/service — below the 0.75 `shouldImport` floor, so the email stays Pending in the review inbox rather than importing), add a warning, and record a `suggested_date` in the parse metadata where a simple heuristic yields exactly one candidate within the window (e.g. same day-of-month in an adjacent month landing on the claimed weekday: 5 June → 5 July 2026). The reviewer accepts or fixes it in the inbox.
   - Tests: the verbatim 5 June subject with `received_at` 2026-07-03 (the curated corrected date −2 days: extracted 2026-06-05 is in the past *and* a Friday despite "sunday" — expect hold + `suggested_date` 2026-07-05, same day-of-month landing on the claimed weekday within the window), a stale past date, a far-future date, and a normal near-future Sunday that must pass untouched.
3. **Multi-service pipeline fix** (Phase 5) — done now, before any archive run.

Note the interplay with the archive harness: `syntheticReceivedAt` = groundTruthDate −2 days means archive entries won't trip the window check spuriously, and because the 5 June entry's ground truth is the *curated* 2026-07-05, its synthetic `received_at` is 2026-07-03 — so the parser validator fires on it exactly as it would have in production (past date + weekday mismatch). It is caught twice: by the archive's `source_date_discrepancy` gate *and* by this validator.

## Phase 5 — Multi-service pipeline fix (approved)

**Schema and DTOs (aligned — per-plan fields live on the plan):**
- `OpenAiOosEmailItemExtractor` schema/prompt → `{"services":[{"service":"morning|evening|other|unknown","date":"YYYY-MM-DD|null","items":[{type,title}],"confidence":0-1}],"notes":[…]}`. `other` covers specials (carols, Christmas) matching the existing `SermonService::Other`. **Per-plan optional date** handles multi-date emails (Christmas weekend emails happen in production too); parser validates plan dates (createSafe + plausibility window vs email date) and falls back to the email-level date.
- Extend `app/Data/OosEmailItemExtractionResult` with `services`; keep flattened `items` for compatibility. New `app/Data/OosEmailServicePlan` DTO: service, date, items, confidence. `app/Data/OosEmailParseResult` gains `servicePlans`; legacy single-service fields stay populated (morning-first) so `storedParseResult()` round-trips old metadata.
- `OosEmailParserService::extractService()` becomes corroborating evidence per plan, not winner-takes-all.

**Importer lifecycle (defined, not naïve):**
- `InboundEmailImportService::import()` accepts `createOnly` and returns a new `OosEmailImportResult`: per-plan outcomes (`created` / `merged` / `skipped_existing` / `held_for_review` / `failed`) with church_service_ids. Create-only existence checks happen **inside the importer's transaction** per date+service pair, and a `UniqueConstraintViolationException` from a concurrent create resolves to `skipped_existing`, not `failed` — under create-only semantics a race loser and a pre-existing service are the same outcome.
- Email status rules: `Processed` only when every plan reached a terminal outcome (created/merged/skipped); any `failed` plan → email keeps its prior status with per-plan state + failure recorded in metadata; re-runs are idempotent because already-created plans resolve to `skipped_existing`. Mixed confidence: a strong plan may import while a weak plan is `held_for_review` — for real emails the email then stays `Pending` (visible in inbox with per-plan state); for archive entries the held plan is simply reported.
- Update the full read/write surface, not just the writers: `ProcessInboundOosEmail`, `app/Actions/InboundEmail/ApproveInboundEmailImport.php` (returns the result; UI redirects to the first `created` service, falling back to the review inbox with a per-plan outcome summary when nothing was created — e.g. all plans skipped or held), `ReparseInboundEmail.php`, `app/Actions/PrefillChurchServiceFromInboundEmail.php`, **`app/Actions/InboundEmail/InboundEmailPreviewFactory.php`**, **`app/Queries/ReviewInboxQuery.php`** (preview shows per-plan state), `ReviewInbox.php` Livewire + blade partials, and the manual-save completion path (`InboundEmailImportService::markAsProcessedFromManualReview()` — **editing/saving one plan must not mark the whole email processed**; record per-plan completion and only flip status when all plans are resolved).
- **Plan addressing for manual edit**: "Edit & approve" currently passes only the inbound email id — with multiple plans that is ambiguous. Introduce a stable plan key (`{service}:{date}`, unique within a parse result) carried through the route/Livewire action, so editing targets exactly one plan and completing it resolves only that plan. Legacy stored parses with only a flattened item list are **not directly approvable** once multi-plan lands: the approve/edit actions must require a re-parse first (one guard clause + a clear message), otherwise a flattened morning+evening blob would import as a single service. Read all of these files before changing them; keep legacy single-service *rendering* working for already-stored parses.

## Phase 6 — Evaluation run on the fixed pipeline, iterate, then backfill

1. `vendor/bin/sail artisan oos:import-archive` (parse + eval only, real LLM, cached) → report. With known bugs fixed, every miss is a *new* finding.
2. Each new finding worth fixing: failing test first, fix, bump parser version (auto-invalidates affected cached parses) or targeted `--fresh-parse --date=...`.
3. When the import gates pass for a satisfactory set: `vendor/bin/sail artisan oos:import-archive --import` — create-only fills missing date+service slots. Local first; environment-agnostic for a later prod run.
